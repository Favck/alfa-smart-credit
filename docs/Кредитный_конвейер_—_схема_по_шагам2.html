Умный кредитный кабинет — схема по шагам

Сквозной процесс: клиентский путь, андеррайтинг, скоринг, оркестрация и соответствие критериям Альфа-Банка.

Статусы заявки (диаграмма состояний — обязательна в репозитории)

DRAFT→SUBMITTED→CHECK→ENRICH→SCORING→REVIEW→ APPROVED/COUNTER_OFFER/NEED_INFO/REJECTED→SIGNING→DISBURSED | CANCELLED

Ключевые нюансы переходов:
• NEED_INFO: при догрузке данных заявка возвращается сразу в ENRICH / REVIEW (с сохранением контекста и обогащенных признаков, без сброса на первичную проверку формы).
• COUNTER_OFFER: клиент согласен → SIGNING → DISBURSED; клиент отказался от встречных условий → CANCELLED (финальный статус отмены).
• Каждый переход строго логируется в таблицу аудита StatusHistory.

Приём и проверка полноты (CHECK)

Что делает бэкенд

Система (моки)

Обогащение данными (ENRICH)

Источники (детерминированные моки)
  • ЕГРЮЛ: статус (действует/ликвидируется), возраст, ОКВЭД
  • «Прозрачный бизнес»: массовый адрес, дисквалификация руководства
  • БКИ: объем обязательств, число закрытых кредитов, просрочки (0 / 30 / 90+)
Реализация
  • Локальные JSON-симуляторы по ИНН заемщика
  • Мгновенный детерминированный ответ без внешних зависимостей
Данные
  • Объект EnrichmentResult фиксируется в БД заявки
Хакатон: реальные АБС и платные сервисы (ФНС, платное БКИ) запрещены. Все внешние контуры эмулируются локальными стабами, зафиксированными в THIRD_PARTY_NOTICES.
5
ML / Скоринг (FastAPI)

Скоринг и оценка риска (SCORING)

Факторы оценки
  • Долговая нагрузка (DTI): платежи / выручка
  • Возраст бизнеса (стаж) и стабильность ОКВЭД
  • Качество кредитной истории (просрочки БКИ)
  • Параметры запроса (сумма, срок, продукт)
Модель и Explainability
  • Скоринговая модель (скоркарта / LightGBM)
  • Расчет вероятности дефолта (PD) и балла (300–850)
  • SHAP / веса признаков: топ-3…5 драйверов скора с понятным текстом
  • Расчет максимальной посильной суммы
Результат для бэкенда
  • score, pd, stop_factors, reasons, max_limit
  • Скоринг дает оценку риска, но не ставит финальный статус
Хакатон: четкое разделение скоринга (математика риска) и кредитного решения (бизнес-логика). Объяснимость (Explainability) — обязательное требование банка.

Сотрудник банка / Кредитный конвейер

Кредитное решение и Кабинет андеррайтера (REVIEW)

КатегорияКритерийРежим принятияДействие конвейера / Андеррайтера
АвтоодобрениеScore ≥ 620, стоп-факторов нетАвтоматическиПереход в APPROVED, формирование оффера клиенту
Пограничный кейсScore 520–619 или крупная суммаКабинет андеррайтераАналитик смотрит Explainability → Одобрить / Снизить сумму (COUNTER_OFFER) / Запросить данные (NEED_INFO)
ОтказScore < 520 или стоп-фактор (просрочка 90+, банкротство)Автоматически / ПодтверждениеПереход в REJECTED с мотивированной причиной простым языком
Функционал экрана андеррайтера (Кабинет сотрудника банка):
  • Очередь поступивших заявок с фильтрацией по статусам и уровню риска
  • Детальная карточка: анкета + выписка + данные моков ЕГРЮЛ и БКИ
  • Блок Explainability: наглядный график вкладов факторов (зеленые плюсы и красные минусы к баллу)
  • Кнопки принятия решения: «Одобрить», «Встречное предложение» (коррекция суммы/срока), «Запрос документов», «Отклонить» (с обязательным текстовым обоснованием)
Хакатон: наличие полноценного интерфейса сотрудника банка — прямое требование экспертов. Автоматизация приветствуется, но ручной андеррайтинг на пограничных заявках отражает реальную практику банка.
7
Клиент

Решение банка и реакция клиента

Действия клиента
  • APPROVED: видит одобренные параметры (сумма, срок, ставка, график) → переход к подписанию
  • COUNTER_OFFER: видит скорректированную сумму/срок → Принять (→ SIGNING) или Отказаться (→ CANCELLED)
  • NEED_INFO: видит запрос андеррайтера → догружает выписку → возврат в ENRICH/REVIEW
  • REJECTED: видит понятные причины отказа (без банковского жаргона)
Статусы
  • SIGNING, CANCELLED, REJECTED или возврат в REVIEW
8
Система (мок)

Подписание договора и зачисление средств

Клиент
  • Просматривает сгенерированный договор
  • Подтверждает согласие (имитация ПЭП: чекбокс согласия / ввод демо-кода)
Система
  • Генерирует PDF-договор с факсимиле и отметкой ПЭП
  • Имитирует проводку зачисления кредитных средств на расчетный счет
Статус
  • DISBURSED (Кредит выдан), запись в историю аудита
Хакатон: сценарий завершается экраном с фактом успешного подписания и перечисления денег. Полноценное сопровождение (графики на 2 года, расчет пени, транши) не требуется.

Данные и архитектура сущностей в БД

Хранение организовано через реляционную модель Django ORM с единым источником правды для статуса заявки:

Архитектурное правило: статус заявки меняется строго по машине состояний. Прямые произвольные апдейты статуса запрещены.

Две проекции системы

Кабинет клиента (Предприниматель)
  • Быстрый вход под готовыми демо-компаниями
  • Каталог кредитных продуктов с рыночными ставками
  • Форма подачи заявки с автоподтягиванием реквизитов
  • Интерактивный таймлайн движения заявки
  • Экран решения: принятие оффера / согласование встречных условий
  • Просмотр и подписание договора (ПЭП) с экраном успешного зачисления
Кабинет сотрудника банка (Андеррайтер)
  • Дашборд и очередь заявок в статусе ручного разбора (REVIEW)
  • Полный профиль заемщика: анкета + финансовые маркеры + БКИ
  • Инструмент Explainability: расшифровка весов и драйверов риска
  • Панель управления решением: Одобрить / Контроффер / Запрос данных / Отказ
  • Аудит-лог действий по каждой кредитной сделке

Технические требования и инфраструктурные ограничения

Ограничения хакатона

  • Веб-интерфейс: десктопная версия обязательна (мобильная адаптация — бонус)
  • Автономность: без SMS, email, звонков и внешних платных API
  • Потребление RAM: стенд в Docker должен укладываться в до 12 ГБ RAM (без весов LLM)
  • Развертывание: запуск всего контура одной командой docker compose up

Требования к LLM (AI-модуль)

  • Open-Weights only: открытые модели (Llama 3, Mistral, Qwen и др. до 120B параметров)
  • OpenAI-compatible API: вынос в .env переменных LLM_BASE_URL, LLM_API_KEY, LLM_MODEL_NAME
  • Роль LLM: реактивный ассистент по продуктам и генерация текстового саммари рисков для андеррайтера
