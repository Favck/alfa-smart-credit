# Альфа.Поток

Репозиторий: https://github.com/VoltusV5/alfa-potok (приватный).

Базовый backend для хакатона: Django 5.2, Django REST Framework, SQLite и Swagger UI.
Frontend перенесён на Vue 3 и Vite в `frontend/`. Материалы хакатона находятся
в `docs/`. Кредитный конвейер пока описан как контракт API.

## Запуск Vue-фронтенда

В отдельном терминале, Node.js `^22.18.0 || >=24.12.0`:

```powershell
Set-Location frontend
npm.cmd ci
npm.cmd run dev
```

Открыть http://127.0.0.1:5173/ и выбрать готовый демо-профиль по клику.
Сохранены экраны прототипа, светлая/тёмная темы и мобильная навигация.
Формы и действия пока используют локальные демоданные без подключения к Django.
Реализована первая серия дизайн-концептов (главная с красной картой,
трёхмерная графика продуктов, форма и таймлайн). Изображения включены в проект,
переходы, анимации и мобильная версия сохранены.
Для production-сборки: `npm.cmd run build`. Подробности — `frontend/README.md`.

## Запуск в Windows

Из корня проекта, Python 3.11:

```powershell
py -3.11 -m venv backend\.venv
& .\backend\.venv\Scripts\python.exe -m pip install -r backend\requirements.txt
Set-Location backend
& .\.venv\Scripts\python.exe manage.py migrate
& .\.venv\Scripts\python.exe manage.py seed_demo
& .\.venv\Scripts\python.exe manage.py runserver 127.0.0.1:8000
```

- Swagger: http://127.0.0.1:8000/api/docs/
- OpenAPI YAML: http://127.0.0.1:8000/api/schema/
- OpenAPI JSON: http://127.0.0.1:8000/api/schema/?format=json
- Проверка сервера и БД: http://127.0.0.1:8000/api/v1/health/

Из корня также можно выполнить `docker compose up --build`, если запущен Docker Desktop.
Команда запускает Django на порту 8000 и Vue/Vite на порту 5173.
Backend автоматически применяет миграции и создаёт демо-пользователей. БД хранится в named volume.
Это локальный демонстрационный сервер Django.
Production: https://alpha.srv-node.com — Gunicorn, статическая Vue-сборка,
HTTPS и CI/CD GitHub Actions. Настройка и откат: [deploy/README.md](deploy/README.md).
Для локального запуска вне Docker БД находится в `backend/data/db.sqlite3`.

## Проверка через Swagger

1. Выполнить `GET /api/v1/auth/demo-profiles/`.
2. Выполнить `POST /api/v1/auth/demo-login/` с `{"profile_id": "green"}`.
3. Скопировать поле `token`, нажать **Authorize**, ввести `Token <полученный токен>`.
4. Выполнить запросы к `/auth/me/`, `/company/`, `/products/`, `/news/`.
5. Повторить вход с `yellow`: персональная лента изменится с производства на торговлю.
6. Профиль `underwriter` имеет роль `bank`. Клиент не может обращаться к банковским операциям.
7. Для выхода выполнить `POST /api/v1/auth/logout/`: токен отзывается.

Все маршруты в шагах 4–7 имеют префикс `/api/v1/`.

Регистрации и паролей нет. `green`, `yellow`, `red` — три клиента, `underwriter` — сотрудник банка.
Выбор профиля из будущего Vue-интерфейса будет вызывать тот же demo-login.
Это вход для синтетического стенда, разрешённый при `DEMO_MODE=true` (по умолчанию).
Отключение режима закрывает список профилей и новые демо-входы; уже выданные токены остаются действительными до выхода/отзыва.
При повторном входе в один профиль используется один токен; выход отзывает его для всех открытых сессий этого демо-профиля.
Демо-пользователи не имеют доступа к Django Admin. При необходимости администратор создаётся отдельно командой `createsuperuser`.

## Что уже работает

- Swagger с локальными JS/CSS (без CDN), OpenAPI 3.0.3, русские описания и схемы запросов/ответов.
- Демо-вход, текущий пользователь, отзыв токена и разграничение ролей.
- Компания текущего клиента, три продукта, статьи и персональная лента по отрасли.
- Healthcheck с обращением к SQLite.

Пользователи и токены сохраняются в SQLite. Компании, продукты и статьи пока представлены локальными синтетическими
справочниками `backend/api/demo_data.py`. Ставки демонстрационные, без обращения к ЦБ или другим внешним сервисам.
ИНН и другие реквизиты вымышлены и не предназначены для проверки реальными реестрами.

## Черновой контракт конвейера

Операции **[ПЛАН]** имеют схемы будущих успешных ответов, но сейчас честно возвращают `501 not_implemented`.
Они не сохраняют заявки, не выполняют скоринг и не принимают кредитных решений.
Защита по авторизации/роли уже применяется. Проверки конкретных заявок и бизнес-переходов будут добавлены при реализации.

Описаны:

- Создание и редактирование черновика, отправка, отмена, список и история заявок.
- Предварительная оценка до отправки, понятные клиенту причины результата.
- Запрос дополнительных данных и ответ клиента.
- Банковское предложение, принятие/отказ, документы, скачивание и имитация подписания/выдачи.
- Очередь банка, детальная карточка с данными моков и скорингом, решения и аудит.

Суммы передаются в целых рублях, ставки — в процентах годовых, время — ISO 8601, идентификаторы заявок — UUID.
Баллы скоринга: 300–850. Статус задаёт сервер, произвольного изменения через PATCH нет.
Внутренний ML API из папки `docs/` не публикуется как браузерный API: вызывать его будет Django.

Допущения для обсуждения: одна компания на клиента, три продукта, выписки без автоматического распознавания,
персонализация новостей по отрасли, LLM вне первой версии. Продуктовые лимиты проверяются сервером при будущей реализации.
Контракт требует уточнить расчёт овердрафта, идентификатор для ML pre-predict до создания заявки,
правила маршрутизации после дозапроса и матрицу автоматических решений.

## Структура и проверки

Инструменты разработки устанавливаются отдельно от runtime-зависимостей:

```powershell
& .\backend\.venv\Scripts\python.exe -m pip install -r backend\requirements-dev.txt
```

Для Black, isort и Flake8 установлена максимальная длина строки **79 символов**.
Настройки находятся в `backend/pyproject.toml` и `backend/.flake8`.
Flake8 проверяет превышение длины строки (E501); исключены только правила
E203 и W503 для совместимости с форматированием Black.

Из `backend/`, форматирование:

```powershell
& .\.venv\Scripts\python.exe -X utf8 -m isort .
& .\.venv\Scripts\python.exe -m black .
```

Проверки без изменения файлов:

```powershell
& .\.venv\Scripts\python.exe -X utf8 -m isort --check-only .
& .\.venv\Scripts\python.exe -m black --check .
& .\.venv\Scripts\python.exe -m flake8 .
```

Флаг `-X utf8` нужен isort для корректной работы с русским текстом
и Unicode-символами в консоли Windows.

Тесты запускаются через pytest из корня проекта:

```powershell
& .\backend\.venv\Scripts\python.exe -m pytest
```

В корне добавлен `pytest.ini`: настройки Django, путь к backend и поиск
существующих Django-тестов в `tests.py`. `pytest` и `pytest-django`
включены в `backend/requirements-dev.txt`.

- `backend/config/` — настройки Django и маршруты Swagger.
- `backend/api/serializers.py` — схемы данных.
- `backend/api/views.py` — рабочие справочники/авторизация и явно отмеченные заглушки.
- `backend/api/urls.py` — маршруты API.
- `backend/openapi.yaml` — проверенная выгрузка схемы; Swagger строит актуальную схему из кода.
- `backend/requirements.txt` — зафиксированные версии всех Python-зависимостей.

Из `backend/`:

```powershell
& .\.venv\Scripts\python.exe manage.py check
& .\.venv\Scripts\python.exe manage.py test
& .\.venv\Scripts\python.exe manage.py spectacular --file openapi.yaml --validate --fail-on-warn
```

Настройки читаются из переменных окружения, пример — `backend/.env.example`.
Сам файл `.env` автоматически не загружается. Для PowerShell, например: `$env:DEMO_MODE = "true"`.
Пока нет PostgreSQL, Redis, Celery и подключения к ML: они не нужны для запуска и обсуждения контракта.
